HOW_TO_RECOMMENDATIONS.md


Руководство по архитектуре и реализации системы «TSPiceLaboratory»

Данный документ описывает рекомендуемый технологический стек, структуру хранения данных, организацию вычислительного конвейера и шаблоны генерации PDK. Ссылки в скобках указывают на закрываемые требования из REQUIREMENTS.md.

1. Технологический стек и границы приложения (FR-UI-*, NFR-PORT-01, NFR-PERF-05)

Система проектируется по принципу Zero-Dependency (автономный исполняемый файл без внешних серверов, JVM, Docker-контейнеров и предустановленного Python у конечного пользователя).
• Вычислительное ядро и оркестрация (Rust): Нативный машинный код, многопоточность без накладных расходов на сборщик мусора (GC) и GIL (rayon для параллельного обхода сеток, faer / nalgebra для разреженных матриц).
• Пользовательский интерфейс и 3D-рендеринг (eframe + egui + wgpu):
	• Нативный Immediate-mode GUI на чистом Rust с прямым рендерингом 3D-сцены через Vulkan/DirectX 12 (wgpu).
	• Нулевое копирование (Zero-Copy) при передаче 3D-слепков из ядра в окно просмотра.
	• Докинг вкладок через egui_dock, перетаскивание шагов техпроцесса через egui_dnd, научные графики ВАХ/ВФХ через egui_plot.
• Внешний API / Интеграционный слой (опционально для автоматизации): Легкий встроенный сервер на Axum + utoipa (не более 5–6 универсальных маршрутов с плоскими JSON-конвертами), вынесенный в отдельный крейт для разгрузки rust-analyzer.
• Упаковка дистрибутива: Статическая линковка зависимостей и флаг bundled для SQLite вшивают все библиотеки внутрь TSPiceLaboratory.exe. Сборка для Windows из-под Linux выполняется через cargo-zigbuild.

Рекомендуемая структура Cargo Workspace

Разделение проекта на 5 изолированных крейтов минимизирует время инкрементальной компиляции и потребление памяти IDE:
1. cad-domain — чистые DTO-структуры, перечисления доменов, контракты ошибок (без зависимостей от БД и UI).
2. cad-storage — слой работы со встроенными SQLite, KuzuDB и Apache Parquet / Arrow.
3. cad-physics — 3D-сетки, трейт операций чистой комнаты, решатели ДУРЧП, инференс ONNX, многостадийный экстрактор Verilog-A и фильтр ОТК (QC Gate).
4. cad-pdk — шаблонизатор (Tera / Askama) для сборки пакетов PDK под целевые САПР.
5. cad-ui — точка входа, окно eframe/egui, 3D-вьюпорт wgpu и телеметрия GPU.

2. Базы данных и хранение артефактов (NFR-DATA-01, NFR-DATA-02, FR-IO-06, FR-CKP-03)

Для исключения комбинаторного взрыва таблиц и сохранения скорости запуска < 50 мс используется гибридная модель из трех специализированных встраиваемых хранилищ внутри одной локальной директории проекта:

2.1. SQLite — реляционное ядро и каталог рецептов (sqlx / rusqlite с флагом bundled)

• Назначение: Хранение плоских справочников, JSON-паспортов материалов, рецептов чистой комнаты, критериев ОТК и реестра запусков.
• Схема без раздувания таблиц (5 базовых сущностей):
	1. materials — паспорта веществ (id, name, material_class, properties BLOB в формате JSONB).
	2. lattices — базовая геометрия и привязка доменов (id, device_domain, geometry_dir, domain_map BLOB).
	3. operations — шаги маршрута (id, recipe_id, step_order, op_type, enabled, params BLOB, state_hash).
	4. requirements — профили испытаний зондовой станции, параметры экстракции и допуски ОТК (stimuli BLOB, extraction_cfg BLOB, qc_criteria BLOB).
	5. simulation_runs — итоговый реестр запусков, ссылки на датасеты Parquet, вердикт ОТК (qc_report BLOB) и путь к собранному PDK (pdk_dir).
• Обязательные PRAGMA при открытии БД:
	• PRAGMA journal_mode = WAL; — разрешает одновременное чтение из UI и запись из расчетного ядра без блокировок.
	• PRAGMA synchronous = NORMAL; — ускоряет транзакции записи без потери надежности.

2.2. KuzuDB — встраиваемая графовая база (kuzu crate, язык Cypher)

• Назначение: Хранение топологических связей и эволюции состояний без тяжелых рекурсивных SQL-запросов.
• Что хранится в графе:
	• Топология слоев: Узлы GeoDomain и ребра TOUCHES (ohmic, schottky, insulator_tunnel) для автоматической постановки граничных условий на стыках материалов.
	• Дерево эволюции и ветвлений: Узлы SiliconSnapshot и ребра EVOLVED_BY для мгновенного обхода истории шагов, кэширования и ветвления экспериментов (FR-CKP-04).
	• Прямой экспорт в GNN: Выгрузка подграфов в формат Apache Arrow для обучения графовых нейросетей.

2.3. Apache Parquet / Arrow и Safetensors — тяжелые бинарные данные

• Запрет на хранение массивов в БД: 3D-сетки, поля потенциала/температуры и осциллограммы ВАХ никогда не записываются в SQLite или KuzuDB.
• Apache Parquet (arrow, parquet crates): Используется для сжатого колоночного хранения 3D-полей (fields_3d.parquet) и кривых (curves_iv.parquet). Позволяет UI считывать только один выбранный столбец (например, только температуру temp_k) и хранить статистику min/max в метаданных файла для мгновенной проверки ОТК.
• Safetensors (safetensors crate): Используется для сохранения бинарных 3D-слепков состояния кремния в кэше и обмена тензорами с моделями ИИ.

3. Разделение доменной области (Bounded Contexts)

Чтобы избежать «проклятия размерности» при одновременной поддержке транзисторов, мемристоров, мемтранзисторов и нейристоров, система делится на 4 изолированных контекста:
1. Контекст Техпроцесса (Process Context): Преобразует параметры чистой комнаты (температура, время отжига, доза имплантации, НТЛ) в эффективные физические константы материала в узлах сетки. Дальше этого слоя параметры чистой комнаты не передаются.
2. Контекст Физики Прибора (Device Physics Context): Разделяется на 4 независимых решателя по типу уравнений:
	• Дрейф-диффузия (транзисторы);
	• Ионный транспорт и рост филаментов (мемристоры);
	• Связанный 2D/3D полевой и ионный домен (мемтранзисторы);
	• Фазовые переходы и тепловая неустойчивость (нейристоры).
3. Контекст Компактной Модели (Compact Model Context): Аппроксимация интегральных кривых в уравнения Verilog-A (I(V) и \(\frac{dx}{dt} = f(V, x)\)).
4. Контекст Экспорта PDK: Шаблонная генерация файлов под целевые САПР.
Прием сжатия признаков: Перед подачей в нейросеть или оптимизатор размерные параметры сворачиваются на стороне Rust в 5–8 безразмерных физических критериев (П-теорема Букингема: число Пекле, отношение тепловой и электрической постоянных времени и др.).

4. Структура 3D-данных и конвейер Checkpointing (FR-CORE-*, FR-CKP-*)


4.1. Метод функций уровня (Level-Set) на разреженном октодереве

• Вместо модификации поверхностных треугольных сеток (.stl), которые дают самопересечения при травлении, границы материалов задаются скалярным полем расстояний φ(x, y, z) = 0 на адаптивной воксельной сетке (Octree) с субнанометровым сгущением на границах слоев.
• Осаждение и травление реализуются как сдвиг изоповерхности φ = 0 вдоль нормали, что математически гарантирует герметичность 3D-структуры (FR-CORE-02). Для отрисовки в wgpu или экспорта во внешние пакеты поверхность извлекается алгоритмом Marching Cubes.

4.2. Конвейер операций и кэширование по BLAKE3

• Каждая операция реализует единый трейт ProcessOperation: \(\text{State}_i = \text{Op}_i(\text{State}_{i-1}, \text{Params}_i)\).
• Для каждого шага вычисляется криптографический хэш:
\(\text{Hash}_{i}=\text{BLAKE3}(\text{Hash}_{i-1}\parallel \text{OpType}_{i}\parallel \text{ParamsJSON}_{i})\)
• При изменении N-й операции в UI ядро находит в кэше SiliconSnapshot с хэшем \(\text{Hash}_{N-1}\), загружает слепок с диска и пересчитывает только цепочку \(N \dots M\).

5. Экстракция моделей и генерация PDK (FR-EXT-*, FR-PDK-*, FR-TNR-*)


5.1. Многостадийная экстракция (Multi-stage Extraction)

Подгонка статических и динамических ветвей в одной функции потерь запрещена. Алгоритм выполняется в 3 последовательные стадии с заморозкой параметров предыдущего этапа:
1. Фиттинг статических ветвей (состояния HRS/LRS или подпороговый ток и \(V_{TH0}\) транзистора).
2. Заморозка статики и фиттинг дифференциального уравнения эволюции состояния \(\frac{dx}{dt}\) на импульсных режимах.
3. Фиксация гладких (C²) вольт-фарадных зависимостей и паразитных емкостей.

5.2. Шаблонная генерация PDK (Tera / Askama)

Экспорт PDK реализуется без подключения тяжелых C++ SDK (например, OpenAccess SDK) через генерацию текстовых файлов и скриптов инициализации из .tera шаблонов:
• Для Cadence Virtuoso (target=virtuoso):
	• techfile.tf и display.drf — слои, маски GDSII, цвета и базовые нормы DRC (minWidth, minSpacing);
	• build_oa_pdk.il — SKILL-скрипт, который при запуске Virtuoso автоматически компилирует techfile.tf в бинарную базу OpenAccess и создает symbol, spectre-вид, форму свойств CDF и параметрическую ячейку топологии PCell;
	• device.va, corners.scs (TT, FF, SS, MC), cds.lib, .cdsinit;
	• Правила DRC/LVS и стек stack.ict для паразитной экстракции в Quantus QRC.
• Для Tanner EDA (target=tanner):
	• model.va, corners.lib, setup_layers.tcl (слои для L-Edit), drc_rules.tcl, .sym (для S-Edit) и testbench.sp (для T-Spice).
• Универсальный минимальный пакет (ngspice, Qucs, MATLAB):
	• device_model.va, corners.lib, tech_layers.json / parasitics.sp и testbench.sp.

6. Производительность и связка с нейросетями (NFR-PERF-*, NFR-REL-03)

• Разделение Training и Inference: Обучение суррогатных моделей и графовых нейросетей (GNN / PINN) выполняется офлайн на Python (PyTorch) на датасетах .parquet, собранных с «виртуальных пластин». Готовые веса экспортируются в .onnx или .safetensors.
• Нативный инференс в Rust (ort или burn): Внутри .exe модели запускаются напрямую через ONNX Runtime (с поддержкой CUDA/DirectML) без вызова Python и накладных расходов на GIL/сериализацию.
• Паттерн Warm Start (NFR-PERF-03): Нейросеть предсказывает стартовое распределение потенциала и заряда (с точностью 95–98%), после чего численный решатель на Rust доводит решение методом Ньютона за 3–5 итераций вместо 100–200.
• Батчинг оптимизации: Вместо последовательного перебора точек ядро Rust формирует батч из 1024–4096 возмущений параметров и прогоняет его через GPU за один такт.
• Защита от нехватки VRAM (NFR-REL-03): Перед выделением памяти на GPU оценивается размер разреженной матрицы; при дефиците видеопамяти или исключении Out of Memory буферы очищаются, а расчет бесшовно переводится на многопоточный CPU-решатель с выводом уведомления в статус-бар egui.
